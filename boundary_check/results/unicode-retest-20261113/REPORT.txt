计数口径
第一轮共 748 个成对请求，第二轮共 942 个成对请求，各自都在两版数据库上执行。
兼容性探针没有竞赛明确预期断言，不能把探针全部算作“通过”。
故障注入覆盖行文件同步、索引同步、目录元数据同步、元数据切换前后和旧文件回收；
其中一个场景还在恢复过程中再次终止进程。两版合计 12 个场景、256 条 SQL 断言、14 次终止。
故障测试使用独立派生镜像和数据卷，库文件只控制终止时点，不修改数据库文件内容。

仍保留的差异
1. Python 基准在 5,000 位数字请求 ID 上返回 id=null 的协议错误；C++ 正确原样回传。
   第一轮测试进程退出码为 1，来源就是这条 Python 基准失败；不是 C++ 测试失败。
2. 重复别名仍有 4 种 SQL、索引建立前后共 8 处 Python/C++ 返回差异。
   这些属于别名引用歧义，未因本次 Unicode 修复改变，也没有把 Python 行为直接作为真值。
3. 第二轮中，两版仍有 22 条响应与测试脚本按 MySQL 文档构造的预期不同，涉及注释、
   转义、别名、排序和语法扩展等。这些是兼容性探针，未连接真实 MySQL 逐条确认；
   其中包含前置语句失败引起的后续差异，不能解释为 22 个独立缺陷。
   它们也不能单独解释“Python 正式用例通过而 C++ 未通过”。

耗时异常与复查
首次记录中，宽表组耗时 4386.692 秒，C++ 行文件同步前崩溃场景耗时 4378.027 秒。
异常原因未确认，原始记录已保留，没有据此计算性能得分。
随后针对性复跑：宽表组 24 个成对请求均通过、无返回差异，耗时 8.402 秒；
同一 C++ 崩溃场景通过，耗时 2.237 秒。耗时是包含驱动及容器操作的测试墙钟时间。
以上复跑未重现卡顿，但不能据此推断首次异常的具体原因。
