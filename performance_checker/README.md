# MiniVectorDB 独立性能检测程序

本目录与数据库实现分离；不修改数据库源码，不包含数据库实现，也不会自动启动 Docker、构建镜像或提交比赛。只有显式执行 `run` 命令才会启动性能负载。默认使用标准库，不需要 NumPy。

## 测量流程

默认每轮生成 10,000 条 128 维 float32 向量，每批 100 条写入并提交；发送 1,000 条 K=10 查询，其中无过滤和普通列等值过滤各一半。数据与查询由公开的固定算法和种子生成，但**未经确认与官方生成方法及隐藏数据一致**。每轮分别使用独立写入容器和查询容器，查询容器内先装载数据、可选建索引和预热，再开始查询计时。

- 耗时 T：预先生成 SQL；写入包括 BEGIN、INSERT、COMMIT 的请求与响应；查询包括每条请求发送和完整 JSON 响应接收，不含预热和事后校验。
- 内存 M：读取容器 cgroup v2 的 `memory.peak`，范围从容器启动到测量结束，包含该容器的缓存和资源读取辅助进程。写入和查询采用不同 cgroup；查询的峰值包含数据装载、建索引和预热。
- I/O B：读取 `io.stat` 中用户明确指定的设备 `major:minor` 的 `rbytes+wbytes`。采集时逐个容器核对 `/data` 文件系统设备编号，并尝试运行 `sync -f`；原始计数和错误均保留。设备无法核实或不匹配、计数缺失或同步失败时，I/O 为 `null`，不能计算综合指标。设备匹配本身不证明全部计数均来自数据目录。
- 正确性：在计时结束后独立进行暴力精确计算，检查结果数量、ID、去重、过滤条件、距离和排序，分别计算两组 Recall@K。数据库正常关闭后，使用另一个容器在原数据卷上重启并核对全部记录的内容。
- 默认三轮；任一轮正确性、已检查的资源条件或任一组平均召回率低于 0.95，均不产生有效综合指标。

## 必须区分的限制

本程序给出的是**本地诊断或估算**，不是平台正式成绩：

1. cgroup 计数在数据库关闭前读取；关闭期间或之后的写入可能没有计入。Docker Desktop 的物理设备映射、文件系统及异步写回归属必须单独验证；`sync -f` 和 `docker exec` 不能自动证明与正式平台统计窗口一致，辅助进程也会影响计数。
2. 官方冷缓存流程、冻结的全部硬性资源限制和真实数据分布尚未由本程序自动验证；本程序无法保证与官方硬件和 cgroup 配置相同。I/O 缺失不会视为零。
3. `resources_ok` 仅表示本地容器成功运行、已读取内存且数据目录同步命令成功；不是对所有正式 CPU、磁盘容量、I/O 带宽及超时限制的确认。
4. 综合指标依赖用户提供的实际基线。应使用官方冻结的写入和查询基线各三轮数据，或各指标的三轮中位数；不要用测试示例、缺失值或未经验证的本地数据冒充官方基线。输入文件里的真实性及测试环境是否匹配仍需人工确认。
5. 输出的综合指标仅用于排序，不能直接变成分数。排名需要正式榜单；只有额外提供已经知道的真实排名，才可以按照题目公式换算分数。

## 运行本地检测

从仓库根目录执行。以下命令是示例，**不会由程序自动执行**：

```powershell
python -m performance_checker.checker run --image minivector-round2:f1b9f4e --output performance-results/run-001
```

`--output` 必须是不存在的新目录。该命令仅创建并清理自身随机命名的 Docker 容器和数据卷，不构建镜像。结果保存在新目录的 `result.json`；运行失败也会保存错误和已经完成的轮次。不提供 `--io-device` 时，会保留原始计数，但 I/O 和综合指标显示不可用。

确认 `/data` 的实际数据设备及写回归属后，可以提供设备编号；如已有真实基线，还可以提供基线 JSON：

```powershell
python -m performance_checker.checker run --image minivector-round2:f1b9f4e --output performance-results/run-002 --io-device 8:96 --baseline path/to/baseline.json
```

上面的 `8:96` 只是设备编号格式示例，**不是本机或官方设备的判断结果**。选用 `ann` 或建立向量索引需显式添加 `--mode ann` 和/或 `--create-index`；默认是 `exact`，不创建索引。测试尺寸、种子和资源限制可以通过 `--help` 查看。

## 对照连续向量缓存

`compare_cache.py` 单独对照两版 C++ 的查询路径，程序仍放在本目录，不参与数据库构建：

```powershell
python -m performance_checker.compare_cache --before minivector-cpp:20261111 --after minivector-cpp:contiguous-20261111 --output performance-results/cache-paired --io-device 8:48
```

请先确认当前数据设备编号；`8:48` 是本次本机测试值。每轮使用相同数据和查询，三轮交替先测旧版/新版；默认 10000 条、128 维、1000 次 exact 查询、K=10，有过滤与无过滤各 500 次，不创建磁盘向量索引。每版使用独立容器和数据卷，分组记录耗时、整个查询容器的 I/O 与内存峰值。仅预热一次无过滤查询，因此等值列表的首次建立计入查询耗时。装载和向量缓存准备不计入查询耗时，但计入资源计数。

两版全部查询结果必须一致，再由独立 Python 精确扫描核验各轮召回率，并对每版做重启持久化检查。报告保存镜像 ID、源码哈希、逐轮数据及中位数。标量条件检查次数按当前代码与工作负载推算，**不是硬件缓存未命中或内存总线流量测量**。该对照不单独测量写入阶段，不生成完整比赛综合分数。

## 精确查询与分块预筛对照

`compare_query.py` 使用相同的 JSONL 驱动，对照修改前镜像、优化后的完整预筛和指定分块方式。统计始终关闭，三轮轮换测量顺序，使用不同种子；每版每轮独立数据卷和容器。默认每轮 10000 条、128 维、1000 次查询，过滤与无过滤各 500 次，K=10。

```powershell
python -m performance_checker.compare_query --before minivector-cpp:profile-20261111 --after minivector-cpp:query-20261111 --blocks 0 32 --output performance-results/query-paired --io-device 8:48
```

请先核实数据设备编号；输出目录必须不存在。`--blocks` 可选 `0`（完整预筛）、`32`、`64`、`128`，仅设置被测数据库的 `MINIVECTOR_SCREEN_BLOCK` 环境变量，不改变客户端请求方式。先进行一次无过滤预热，首次等值列表建立仍计入查询时间。所有响应逐项对照，计时后对每轮全部查询执行独立 Python `math.fsum` 精确扫描，并逐版验证重启持久化。报告含镜像 ID、源码哈希、分组耗时、I/O 与峰值内存；资源范围包含装载和预热，不测硬件缓存未命中，不计算完整写入/查询综合指标。

内核微基准和边界检查位于 `tools/test_distance_screen.cpp`，测试通用/AVX2、完整/分块、上下边界、并列、极端 float32、非整块维度。微基准采用固定精确 Top10 边界，仅反映预筛内核开销，不等同于完整 SQL 性能。

`measure_query_cpu.py` 是补充诊断，需在带有数据库可执行程序的 Linux 容器内运行，并让本目录可导入。它让 Python JSONL 客户端和数据库处于同一容器，装载一次数据，三次重新启动数据库并预热，再执行相同的 1000 次查询；`--block` 选择预筛方式。同时读取数据库 `/proc/<pid>/stat` 的用户态与内核态 CPU 时间，报告系统计时粒度。该结果用于区分数据库计算与跨环境通信等待，不替代原 Windows 客户端的端到端对照，不产生 I/O、内存或综合分数。

2026-11-11 [三轮完整负载结果](results/query-20261111-paired/result.json)：修改前/完整预筛/32 维分块的 1000 次查询中位数为 1514.01/1422.78/1388.85 ms，全部 3000 次查询精确核验通过。[同容器 CPU 对照](results/query-20261111-cpu.json)为 540/380/420 ms，计时粒度 10 ms；完整模式的 CPU 用量更低，分块相对完整模式的主对照逐轮优劣存在反转，因此默认仍使用完整预筛。详细分组、资源和限制见[项目说明](../README.md)。

## 分项统计与检测

C++ 数据库的诊断开关默认为关闭。进程启动时设置 `MINIVECTOR_PROFILE=1` 后，会将以 `MINIVECTOR_PROFILE ` 开头的 JSON 行写到 stderr，stdout 仍只用于正式协议。每条记录包含 `kind`、从 1 开始的请求 `sequence`、`wall_ns` 和各项累计的 `ns`、`calls`；启动记录序号为 0。请求记录在响应输出完成之后写出，正常关闭也有记录。没有记录 SQL 或请求 ID。启用时必须持续读取 stderr，避免管道填满阻塞进程。

```powershell
python -m performance_checker.profile_phases --image minivector-cpp:profile-20261111 --reference-image minivector-cpp:contiguous-20261111 --output performance-results/phases --io-device 8:48
```

`--output` 必须是新目录；设备编号应先核实。程序在独立容器中依次运行可选的旧镜像、当前镜像关统计和开统计三种情况，记录每个请求和按操作分组的汇总；默认 10000 条、128 维、1000 次精确查询，先预热一次无过滤查询，首次等值列表建立计入查询阶段。两种或三种模式的所有查询响应必须完全一致，并独立精确检查默认 20 次查询（两组各 10 次）；可用 `--verify-queries` 扩大核验数量。`result.json` 保存汇总与复现信息，各 `*-requests.jsonl` 保存逐请求数据。数据装载后会另起容器核验持久化。该诊断是单次测量，不计算完整性能指标或官方排名。

数据库内各分项的边界如下：

| 字段 | 统计范围 |
| --- | --- |
| `protocol_parse` | 单行 JSON 协议校验和解析，不含读取输入等待 |
| `sql_parse` | SQL 分词和语法解析，数据库执行之前停止计时；包含语法错误 |
| `vector_literal_parse` | 带引号向量字面量的 JSON 解析；不重复统计存储行内的解码 |
| `stored_row_decode` | 存储行 JSON 解析与类型解码，不含读文件等待 |
| `filter` / `filter_lists` | 条件判断 / 等值行号列表查找和构建，包括构建所需扫描 |
| `distance_exact` / `distance_screen` | 精确距离 / 保守预筛距离计算；精确距离包含结果投影中的计算 |
| `heap` | TopK 堆的准入比较、push/pop 及外部归并堆操作；不包含最终排序和所有堆顶读取 |
| `file_sync` | 文件 `fflush`、`fsync`（Windows 为 `_commit`）与关闭 |
| `directory_sync` | Linux 目录打开、`fsync` 和关闭；Windows 当前不执行该操作 |
| `collect` | 计算活跃文件、缓存失效、遍历目录及删除孤立文件 |

请求 `wall_ns` 从读到完整请求行之后开始，到响应刷新之后结束，不含等待输入和输出诊断记录本身。各分项不包含在其他分项内；`engine_other_ns` 包含文件读取、写入、排序、结果序列化、缓存构建中未单独计时的部分、未计时逻辑和部分统计开销。事件统计包含失败请求中实际执行过的阶段。

客户端另测 JSON 编码、响应 JSON 解码和完整往返耗时，以及 Python 主线程、请求发送线程写入与刷新的 CPU 时间和 stdout 读取调用的线程 CPU 时间；这些线程计数不包含读取线程的其他逻辑、stderr 接收线程、Docker 和操作系统的工作。如果环境没有线程 CPU 时钟，相应计数为 null。**短请求的线程 CPU 时间可能受时钟粒度限制显示为零，不代表没有 CPU 开销**；报告同时提供整个装载循环和查询循环的 Python 进程 CPU 时间，包含本检测进程的采集和记账工作，不包含 Docker 或数据库子进程。进程计时也可能受粒度限制，如果读数为零则记录为 null，表示无法可靠测量。

往返时间减去数据库请求耗时只是带符号的残差，混合了编码解码、管道通信、线程与进程调度以及测量边界差异，**不能当作纯驱动 CPU 时间**。启用时每次过滤和距离计算都要读取时钟，会明显影响热路径；请以关闭统计的结果衡量性能，以开启统计的结果定位开销。资源计数从容器启动开始，包含装载与预热。

2026-11-11 本机一次示例：[完整汇总](results/profile-20261111-report/result.json)、[开启统计逐请求数据](results/profile-20261111-report/enabled-requests.jsonl)。10,000 条、128 维、1,000 次查询（过滤与无过滤各 500 次），以下是开启统计时的累计墙钟时间，准备阶段单列：

| 阶段 | 耗时 | 范围 |
| --- | ---: | --- |
| 协议、SQL、向量字面量解析 | 76.62 ms | 1,000 次查询 |
| 过滤及列表查找/构建 | 30.54 ms | 1,000 次查询 |
| 精确距离及保守预筛 | 552.56 ms | 1,000 次查询 |
| 堆操作 | 10.35 ms | 1,000 次查询 |
| 存储行解码 | 215.44 ms | 一次预热，查询阶段不重复读取 |
| 文件同步 | 1,799.46 ms | 100 批插入及其提交 |
| 目录同步 | 568.86 ms | 100 批插入及其提交 |
| 目录回收 | 20.18 ms | 100 批插入及其提交 |

同一批负载关闭统计时 1,000 次查询耗时 1,391.17 ms，开启后 1,820.74 ms，约增加 30.9%；这是单次本地诊断，不作为稳定加速比。开启统计时查询客户端编码与解码分别约 20.90 ms 和 24.39 ms；客户端往返减数据库墙钟时间约 884.97 ms，其中包含通信、调度等无法单独归因的部分。三种运行方式的 1,000 次查询响应一致，并分别验证重启持久化；各抽取 10 次过滤和无过滤查询进行独立精确核验，Recall@10 为 1.0。

## 使用已有测量计算指标

基线 JSON 可直接给每阶段的三轮中位数：

```json
{
  "write": {"time_ms": 100, "io_bytes": 1048576, "memory_bytes": 1048576},
  "query": {"time_ms": 100, "io_bytes": 1048576, "memory_bytes": 1048576}
}
```

**上面数字仅为说明格式的虚构数值，不是官方基线。** 也可使用 `{"rounds":[...]}` 提供恰好三轮；每轮含 `write`、`query` 两个对象，每个对象含 `time_ms`、`io_bytes`、`memory_bytes`。程序会分别取每个指标的中位数作为基线。参考 [基线模板](baseline.template.json)。

对已有结果文件计算：

```powershell
python -m performance_checker.checker score --baseline path/to/baseline.json --measurements performance-results/run-002/result.json
```

每轮按 `R=(baseline+ε)/(actual+ε)`、`f(R)=R/(1+R)`，计算写入和查询各自的 `0.6f(R_T)+0.2f(R_B)+0.2f(R_M)`，再计算 `E=(E_write+2E_query)/3`。时间平滑常量是 1 ms，I/O 和内存各为 1 MiB。最后取**三个每轮 E 的中位数**，四舍五入六位小数；不能把每轮最好的指标拼起来。需查已知正式排名对应分数时，才添加 `--rank N`；该排名由使用者提供，程序不生成排名。
