## 2. 目标与计分

正确性优先，在固定输入、SQL、计时方式和资源条件下减少构建、分词、查询的端到端耗时。

单项官方下降率：r_i = 1 - T_candidate_i / T_official_baseline_i。

综合下降率 R = (mean(3 项构建 r) + mean(2 项分词 r) + mean(4 项查询 r)) / 3。

性能分 = 100 × clamp(R, 0, 0.5) / 0.5。

- 单项构建、分词、查询权重分别为 1/9、1/6、1/12；退化保留负值参加平均。
- 本地新增下降率另算 d_i = 1 - T_candidate_i / T_B0_i，同样先在类别内平均，再三类等权。该数值不代替正式评分。
- 优先研究同时影响分词和构建的开销，但最终按剩余热点、端到端收益、资源成本及风险排序。
- 仅查询改善、其他两类不变时，即使查询耗时接近零，综合下降率也最多约 1/3，达不到 50% 的满分门槛。
- 不承诺未经测量的百分比。正式环境若已稳定封顶，优先确保正确性与可复现性，再决定是否值得扩大修改面。

## 4. 阶段一：定位失败并建立 B0 实测基线

先调查词典缓存测试中的间歇性 `OB_ENTRY_NOT_EXIST`，不以重跑通过代替解释：

1. 对照失败与成功运行，记录同一个词典各 range 的插入、读取、缓存键、哈希、是否发生淘汰、持有句柄及线程时序；分别重跑单用例、完整 Storage 套件及多套件并行场景。记录复现条件和次数，不把 10 轮中的 1 次失败当作真实故障概率。
2. 已确认 `ObDictCacheKey::operator==` 比较 `name_` 和 `dict_type_`，而 `hash()` 还包含 `range_id_`。对同名同类型但 range 不同的两个键，比较结果相等且哈希值可能不同；这违反常规哈希键的相等/哈希一致性要求。增加覆盖不同 range 和可能碰撞的针对性验证，并结合缓存容器实际比较路径判断其影响；目前尚无证据证明这是本次失败的根因。
3. `get_builtin_dict()` 对缓存未命中有 `build_cache()` 回退，而测试直接要求随后的 `load_cache()` 命中。核实缓存淘汰是否允许这种未命中，并区分产品行为错误与测试对缓存驻留作出的不合理假设。若需修改测试，必须保留对实际 API 契约和词典结果的有效断言，不能仅通过重试掩盖缺陷。
4. 根据证据修复对应的产品或测试缺陷；补充针对性回归，在 WSL 的 Bazel 入口重跑 Share、Storage、SQL 完整套件及与复现条件相应的重复/并发测试。记录仍有的不确定性，不能以有限次数通过证明问题绝不复发。

上述定位和必要修复已完成，结果见基线验证报告。后续建立性能数值基线：

1. 在独立 Linux 构建目录构建 B0，固定编译器、优化选项、Unity、分配器和依赖。按用户指定使用 WSL/Bazel，保留仓库默认 opt/O2 和模块检查；构建声明修复单独记录，不将修复工作计作性能收益。
2. 固定 CPU 集、内存限制、客户端位置、数据库配置和后台负载，记录频率/限流、OOM、RSS、CPU 与 I/O；资源数值依据实际环境，不照搬旧机器。
3. 运行已有相关单元测试、SQL 回归与完整结果差分，保存 token、DOC_ID、可观察分数和错误；独立核对期望结果，防止把已有问题固化。
4. 在专用实例运行至少三轮完整 B0 基准，每轮使用新报告文件并重新导入、构建。脚本会删除并重建 fts_large_bench 库。
5. 单独做不计分的剖析运行，用环境支持的 perf stat/record、分配分析和等待/I/O 统计，分别识别构建、分词、查询的 CPU 与等待成本。
6. 保存四条基准查询的执行计划，确认评分、回表、批次及 LIMIT 实际路径。SELECT 1 仅观察客户端和协议底噪，不从官方计时中扣除。

完整基准固定参数：

~~~text

SAMPLES=3 WARMUP=30 SKIP_LOAD=0
~~~

产出：构建清单和二进制哈希、三轮原始报告、九项指标与波动、资源曲线、执行计划、正确性结果及热点排序。

| 编号 | 候选与具体入口 | 进入条件与实施方向 | 验证和退出条件 |
| --- | --- | --- | --- |
| C1 | TOKENIZE 参数及临时对象：ob_expr_tokenize.cpp::parse_param/tokenize_fulltext | 分别计量参数解析、helper 初始化、token map 创建、分词和 JSON。初始化占比显著时，先消除一次调用内重复工作，再研究执行上下文内有容量上限的复用 | 覆盖预处理参数变化、重扫、属性、字符集、字典有效性；不保留临时 arena 指针。收益不足或重置逻辑过于复杂则放弃 |

C2 不直接借用短命输入替代拥有所有权的 token。任何减少拷贝都先证明消费者在下次分词及解析器销毁后是否仍持有数据。

| 编号 | 候选 | 进入条件 | 限制 |

| C5 | 查询批次衔接：ob_text_daat_iter.cpp、ob_text_retrieval_token_iter.cpp、ob_das_text_retrieval_merge_iter.cpp | 当前查询仍有显著投影、比较、批次或复制热点 | 不扩大不算分规则，不硬编码词数、SQL 或结果；覆盖 1/2/3 及更多词、评分、重扫和不同 DOC_ID |
| C6 | 构建跨文档批次填充 | 低填充率确实是主要成本，且 C3 不足以解决 | 先设计批次所有的数据、复制成本、内存上限和失败清理，再测净收益 |

C6 的关键约束已经从当前实现确认：一批输出可能引用 fts_index_ 的文档 arena，下一文档的 segment 会重置它。因此不能直接在输出半批后读取下一文档；跨文档输出必须先解决所有权。

查询侧也不能直接提前 refill：TextMembershipBatchUnion::merge_ids 返回的 ID 可能借用耗尽输入批次的缓冲。提前补充输入必须延长其有效期或复制数据，并将额外成本计入收益。

当前不将 COUNT/LIMIT 重写扩展、通用字符比较/JSON/CRC 改写、SIMD、加并行度或完整 TOKENIZE 结果缓存列为默认工作项。只有新的热点证据和语义证明支持时再立项。

## 8. 候选验收与停止条件

1. 一个候选对应一个可测假设，独立改动、回归及提交，便于单独回退；不叠加未经测量的候选。
2. 相关正确性测试通过后，至少做三组 B0/候选交替完整测试。保持构建、资源、客户端、缓存政策一致；测试不与编译争用资源。
3. 保留九项原始指标、类别平均、本地综合增量、官方格式参考分和资源变化。内置三组 sample 不等于三次独立完整运行；不能只报最好一轮。
4. 收益需在重复中复现，并与实测噪声区分。三组只是起点，接近波动时追加交替样本，不给少量样本包装虚假的统计确定性。
5. 任一计分项出现超过 B0 波动的持续退化，或 CPU/RSS/I/O 明显增长，都需解释后决定取舍；没有解释前不纳入最终组合。
6. 热点占端到端耗时比例 p，局部加速 s 倍时，总耗时下降理论上限为 p × (1 - 1/s)。上限不足以覆盖噪声或实现成本时停止该方向。
7. 若客户端/协议或不可优化等待占主导，降低代码收益预期；不改变官方计时，不扣 SELECT 1，不通过减少输入或跳过必要处理制造收益。
8. 五个官方基准输入文件和评分基线内容保持不变，用哈希核对。正式成绩以统一评测为准，本地报告标明参考性质。
